| 27 | 2026-08-19 | Alembic driver | **asyncpg for both app and migrations.** No psycopg2. | Supersedes the plan in `KNOWN_ISSUES` D-5, which assumed the conventional async-app / sync-Alembic split. Alembic's native async support (`async_engine_from_config` + `connection.run_sync`) removes the split entirely: one dependency, no URL rewriting between drivers, and no chance of the two URLs being "helpfully" reconciled later and breaking one. Rationale is commented in `database/migrations/env.py` so it isn't undone. | asyncpg + psycopg2 (the commonly documented pattern — more dependencies and a standing footgun for no benefit here) | No |
| 28 | 2026-08-19 | UUID generation | Rely on PostgreSQL core `gen_random_uuid()`; **no `pgcrypto` extension** | Built into core since PG 13, and `ARCHITECTURE.md` targets 15+. Requiring an extension adds a superuser step on managed hosts for nothing. `DATABASE_CONTRACT.md` §10 originally listed pgcrypto; that was over-cautious. `0001_baseline` enforces the version floor with a clear error instead. | `CREATE EXTENSION pgcrypto` (needed only for PG < 13); application-side UUID generation (loses the database default) | If a deployment target below PG 13 ever appears |
| 29 | 2026-08-19 | Full-text search vectors | PostgreSQL **STORED generated columns**, not triggers | The database maintains `search_vector` itself, so there is no trigger function to keep in sync with the model, and SQLAlchemy knows never to write the column. `to_tsvector` with a literal regconfig is IMMUTABLE, which is what makes it legal in a generated column. Requires PG 12+. | Trigger + function per table (more moving parts, easy to forget in a migration); application-side vector computation (writes can bypass it) | If the vector needs a configuration that isn't IMMUTABLE |
| 30 | 2026-08-19 | Password hashing library | `bcrypt` (direct), **not** `passlib[bcrypt]` | Deviates from `ARCHITECTURE.md`'s stack table. Verified directly in this environment: `passlib` (last released 2020, unmaintained) probes `bcrypt.__about__` to detect the backend version; that module was removed in `bcrypt` 4.1+, so `passlib.hash()` raises `AttributeError` on first call with the currently-resolved `bcrypt` 5.0.0. This is a real, current break, not hypothetical — reproduced before deciding. `python-jose` for JWT is unaffected and unchanged. | Pin `bcrypt<4.1` to keep `passlib` working (reintroduces a stale, unmaintained dependency purely to satisfy another unmaintained wrapper); wait for a `passlib` fix (project has been dormant since 2020) | If `passlib` ships a fix, or the team standardizes on it elsewhere |
| 31 | 2026-08-19 | Refresh token format | Opaque random string (`secrets.token_urlsafe(32)`), **not** a JWT | The `refresh_tokens` table (Phase 4) is the sole source of validity — revocation, expiry, and rotation are all decided by the database row, never by anything encoded in the token. A JWT refresh token would carry a self-describing payload that still has to be ignored in favor of the DB check, which is pure redundant complexity for zero benefit. Hashed with plain SHA-256 for storage (not HMAC, not bcrypt) — the token already carries 256 bits of randomness, so there is no offline-guessing attack a secret key or slow hash would defend against; only preimage resistance matters, which SHA-256 provides. | JWT refresh token with a `jti` tracked in the DB (adds a signing/verification step that changes nothing about how validity is decided) | No |
| 32 | 2026-08-19 | Refresh-token reuse handling | A revoked/rotated-away refresh token presented again triggers **lockout of all of that user's active refresh tokens**, returning the identical generic error as any other invalid token | Standard OAuth2 refresh-token-rotation reuse detection. A rotated-away token being replayed is a signal of possible theft; the safe response is to kill the whole session family, not just reject the one request. Returning the same error/message as "token not found" or "expired" (rather than a distinguishing one) prevents an attacker from using the response to confirm reuse was specifically what was detected. | Reject only the reused token, leave its replacement valid (leaves a stolen-but-undetected token family alive); return a distinct "reuse detected" error (tells an attacker their replay was noticed) | No |
| 33 | 2026-08-19 | Registration vs. login disclosure | Registration reveals *which* field conflicts (`EMAIL_ALREADY_EXISTS` vs `USERNAME_ALREADY_EXISTS`); login returns the **same** generic error for wrong email, wrong password, and inactive account | Different endpoints, different disclosure risk. Registration's entire purpose is telling the user whether they already have an account — hiding that would just produce a confusing UX for zero security gain, since the user is asserting an identity they claim to already control. Login must not let a caller distinguish "no such account" from "wrong password," which would let an attacker enumerate valid emails. | Generic error on registration too (unnecessary UX cost, no established security benefit for this endpoint); revealing, specific errors on login (classic user-enumeration vulnerability) | No |

| 34 | 2026-08-19 | User preferences storage | JSONB column `users.preferences`, **not** a `profiles` table | SD-3 rejected `profiles` ("users already carries the fields; split adds a join for nothing"), so preferences are a column on the existing table. JSONB by the contract's own rule - preference keys are UI concerns owned by P1 and will change without backend involvement; columns would mean a migration per toggle. The backend bounds size/shape (64 keys, 16 KB, 1 level of nesting) without interpreting meaning. | A `profiles` table (explicitly rejected); typed columns per preference (migration churn); unbounded JSONB (unvalidated document store) | If preferences grow structure worth querying on |
| 35 | 2026-08-19 | Update-schema strictness | Every update schema uses Pydantic `extra="forbid"` | Pydantic's DEFAULT silently DROPS unknown fields, so `PATCH {"role":"admin"}` would return 200 and look successful to an attacker while changing nothing - and would start working the day someone adds `role` to the model. `forbid` makes it an explicit 422. Updatable fields are an allow-list, never a deny-list. 13 escalation vectors are covered by parametrized tests. | Default (silent drop) - looks identical in the happy path and fails open on future edits | No |
| 36 | 2026-08-19 | Unowned-resource response | Return **404**, never 403, for a row owned by someone else | A 403 confirms the id exists, which is an enumeration oracle: an attacker can walk ids and learn which projects/vehicles/conversations are real. 404 is indistinguishable from "never existed", so nothing leaks. Applied uniformly in `core/authz.py` and to soft-deleted projects. | 403 (leaks existence); 401 (wrong - the caller IS authenticated) | No |
