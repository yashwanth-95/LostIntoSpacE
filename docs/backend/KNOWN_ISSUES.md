# Backend Known Issues

**Last audit:** 2026-08-18 (Checkpoint 0/1) · **Last updated:** 2026-08-19 (Phases 6-15)
**Companion doc:** [`BACKEND_STATE.md`](BACKEND_STATE.md) (inventory/architecture — read that first for context)

This is the issues backlog: problems, missing pieces, duplication risk, and dangerous decisions. Resolved items are struck through with the phase that closed them rather than deleted, so the reasoning stays traceable. Nothing here is severity-ranked beyond its grouping.

---

## 1. Summary

Most items are **documentation inconsistencies**, **design gaps**, or **decisions that need making explicitly** so they don't get made by accident. The exceptions worth knowing about:

- **P-10 is the top open risk.** The database migrations have never been applied to a real PostgreSQL server, because none is installed on this machine. They are verified as far as is possible without one, which is not the same as working.
- **P-7 is a genuine defect in a shipped spec** — `RKT_SPEC.md`'s worked example describes a physically impossible rocket. It is not a style issue.
- **P-9 records four places where the architecture docs and `SIMULATION.md` contradict each other**, one of which (coordinate frame) would make stored telemetry meaningless if left unresolved.

Backend application code exists as of Phase 2, database models/migrations as of Phase 4, authentication as of Phase 5, and the full domain API surface as of Phases 6-12. Four real defects have been found and fixed so far (P-11, P-12, P-13, and an offline-mode break in the baseline migration); 214 tests, lint, format, and type checks all pass.

**P-14 now sits alongside P-10 as the top risk:** ownership isolation between users is implemented and asserted, but those assertions only run with a live database.
